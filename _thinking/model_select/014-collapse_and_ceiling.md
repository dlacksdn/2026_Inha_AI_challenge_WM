## 3. 발견 1 — DINO 점수를 쪼개 보니 병목이 둘이었다

### 3.1 왜 쪼갰나

DINO 는 16프레임 각각의 거리를 **평균**한 값이다. 그래서 0.221 이라는 숫자 하나만으로는
아래 두 가지가 구분되지 않는다.

- **(A) 재구성 병목**: 첫 프레임(t=0)부터 이미 틀린다 → 모델이 "주어진 사진"조차 못 그린다
- **(B) 드리프트 병목**: t=0 은 맞는데 뒤로 갈수록 벌어진다 → 움직임 예측이 틀린다

**(A)면 학습을 더 해도 안 내려가고, (B)면 내려간다.** 그래서 반드시 갈라야 했다.

### 3.2 결과 (홀드아웃 96표본)

| 예측기 | t=0 | t=15 | 드리프트(t15−t0) | 평균 |
|---|---:|---:|---:|---:|
| 1.1B step500 | 0.04924 | 0.32995 | 0.28070 | 0.24191 |
| 1.1B step1000 | 0.04757 | 0.29654 | 0.24897 | 0.22074 |
| static | 0.00357 | 0.19181 | 0.18825 | 0.12308 |

읽는 법:
- **드리프트는 학습으로 줄고 있었다**: 0.28070 → 0.24897 (−11.3%). (B)는 개선 중이었다.
- **t=0 오차 0.048 은 거의 안 줄었다**: 0.04924 → 0.04757 (−3.4%). (A)는 요지부동.
- static 은 첫 프레임을 그대로 복사하므로 t=0 이 0.004 다(영상 압축 손실만).

> **여기서 이상한 점**: 첫 프레임은 문제에서 **입력으로 주어진 사진**이다. 그런데 왜 0.048 이나 틀리나?

## 4. 발견 2 — 넘을 수 없는 바닥 0.045 (오늘 최대 수확)

### 4.1 VAE 가 뭔지부터

확산모델은 픽셀을 직접 다루지 않는다. **VAE(오토인코더)** 로 영상을 8배 작은 "잠재(latent)"로 줄인 뒤
그 안에서 그림을 그리고, 마지막에 다시 픽셀로 되돌린다.

*비유*: 그림을 축소 복사해서 작업하고 다시 확대하는 것과 같다. **왕복만 해도 원본과 미세하게 달라진다.**

### 4.2 그 손실을 직접 쟀다

정답 영상을 그대로 VAE 에 넣었다 뺀 뒤 DINO 를 재봤다 (n=32).

| 잠재 추출 방식 | 정답영상 왕복 | 정지영상 왕복 |
|---|---:|---:|
| sample (현재 코드가 쓰는 방식) | **0.04518** | 0.04299 |
| mode (분포의 평균값) | 0.04517 | 0.04299 |

**생성물의 t=0 오차 0.04757 과 거의 같다.** 즉 첫 프레임 오차는 UNet 이 못 그려서가 아니라,
**잠재공간을 쓰는 구조 자체의 대가**다. 학습으로는 절대 없앨 수 없다.

> 부수 확인: `get_first_stage_encoding` 이 분포에서 무작위로 뽑는(`sample`) 방식을 쓰는데,
> 평균값(`mode`)으로 바꿔도 0.00001 차이라 **여기엔 손잡이가 없다.**

### 4.3 그래서 목표가 이렇게 바뀐다

```
DINO 목표 (static 격파)   0.1248
이 파이프라인의 바닥       0.045   ← 정답 영상조차 이 값
──────────────────────────────────
드리프트에 쓸 수 있는 예산  0.0796

현재 드리프트 기여          0.173   (0.221 − 0.048)
static 의 드리프트 기여     0.119
→ 드리프트를 지금의 46% 수준까지 줄여야 한다
```

**싸울 수 있는 구간이 생각보다 훨씬 좁다.** 이걸 모르고 있었다면 "학습을 더 하면 언젠가 되겠지"라는
막연한 기대로 며칠을 태웠을 것이다.

## 5. 발견 3 — 학습이 모델을 망가뜨리고 있었다 (013 가설 붕괴)

### 5.1 궤적 (전부 배치 4 로 통일해서 잰 값, 96표본)

| 누적 스텝 | DINO | Video | Action | TOTAL |
|---|---:|---:|---:|---:|
| 1,000 | 0.2282 | 0.0857 | **1.2171** | **0.5811** |
| 2,000 | 0.2543 | 0.0913 | **1.2178** | 0.5908 |
| 3,000 | 0.3977 | 0.1240 | 1.2554 | 0.6587 |
| 구간 변화 | +0.026 → **+0.143** | +0.006 → **+0.033** | +0.001 → **+0.038** | +0.010 → **+0.068** |
| (참고) static | 0.1231 | 0.0911 | 1.2402 | 0.5603 |

**1,000→2,000 은 거의 정체인데, 2,000→3,000 에서 7배로 무너진다.**

### 5.2 "일시적으로 나빠졌다 더 좋아지는 것" 아닌가?

타당한 의문이고, 실제로 그런 현상이 있다. 지도학습에서도 **epoch-wise double descent**(학습을 계속하면
테스트 성능이 나빠졌다 다시 좋아지는 구간), **grokking**(한참 정체하다 갑자기 일반화) 같은 것이 보고돼 있다.
특히 우리는 `action_embed` 를 0으로 초기화해 **액션의 영향이 정확히 0인 상태**에서 출발했으므로,
액션이 개입하기 시작하며 UNet 이 재조직되는 과도기에 일시적으로 나빠지는 것도 자연스럽다.

그래서 **점 두 개로 단정하지 않고 궤적을 쟀다.** 결과는 회복 조짐 없는 **가속 악화**다.
double descent 라면 어딘가 바닥을 찍고 올라와야 하는데 그 모양이 아니다.

### 5.3 loss 는 끝까지 아무것도 알려주지 않았다

```
누적 1000~1199 : 0.0695     누적 2000~2199 : 0.0633
누적 1200~1399 : 0.0649     누적 2200~2399 : 0.0727
누적 1400~1599 : 0.0647     누적 2400~2599 : 0.1011   ← 최대 0.3698
누적 1600~1799 : 0.0806     누적 2600~2799 : 0.0597
누적 1800~1999 : 0.0723     누적 2800~2999 : 0.0914
학습률: 3.6e-6 에서 warmup 정상 작동 → 1e-4 유지
```

DINO 가 0.228 → 0.398 로 74% 나빠지는 동안 **loss 는 0.06~0.10 사이에서 평탄했다.**
발산도 폭주도 없다. 013 이 "loss 는 터졌는지 확인용"이라고 했지만, 이 정도로 무력할 줄은 몰랐다.

> **교훈**: 이 프로젝트에서 loss 를 보고 학습 진행을 판단하면 안 된다.
> **반드시 홀드아웃 채점으로만 판단한다.** loss 만 믿고 밤새 돌렸다면 9.5시간을 통째로 날렸다.

### 5.4 범인은 학습률로 보인다

`base_learning_rate: 1e-4` 는 **11M 모델용 값을 그대로 가져온 것**이다. config 주석에도
"1.46B warm-start 에 적정한지는 판단할 항목"이라고 미결로 남아 있었다.
131배 큰 모델을 유효 배치 2(배치1 × 누적2)로 돌리면서 같은 학습률을 쓴 셈이다.

*비유*: 작은 배를 몰던 감각으로 큰 배의 키를 같은 각도로 꺾으면 배가 뒤집힌다.

| 배치:DDIM스텝 | 표본당 | 216샘플 환산 | 판정 |

| 1:50 (기존) | 23.33초 | 84.0분 | ✗ 대회 예산 24분 초과 |

원인은 단순했다. 주최측 `generate_baseline_videos.py` 의 기본값이 `batch_size: 1` 인데,

> 비교하기 전에 검증했다: 같은 체크포인트를 배치 1과 4로 각각 생성해 **짝지은 비교**를 하니
> `batch1 − batch4 = −0.00751 ± 0.00701, t = −1.07` 로 **유의하지 않았다.** 배치 4를 써도 된다.

## 8. 사고 — 학습이 하루에 두 번 죽었다

두 번 다 **에러 한 줄 없이** 진행 표시줄 중간에서 끊겼다. 에러가 없다는 건 보통 SIGKILL 을 받았다는 뜻이다.

### 8.1 아닌 것부터 지웠다

| 후보 | 판정 근거 |
|---|---|
| 재부팅 | `uptime -s` = 07-28 23:31. 2일 넘게 켜져 있었다 |
| 로그아웃 | `user@1000.service` 시작 시각이 07-28 23:35 로 **한 번도 재시작 안 됨** |
| 커널 OOM killer | `journalctl -k` 에 흔적 없음 |
| 디스크 가득 | 1.9T 여유 |

> 처음엔 `Linger=no`(로그아웃하면 사용자 서비스가 정지되는 설정) 때문이라고 판단했으나,
> 서비스 시작 시각을 확인하고 **철회했다.** 시스템 설정을 건드릴 필요가 없다는 뜻이기도 하다.

### 8.2 확실한 사실

```
18:09:48  systemd-oomd: 사용자 슬라이스 메모리 압박이 90.82% > 임계 50% 를 20초 이상 지속
          → Chromium 을 죽임
```

이 머신은 `user@1000.service` 에 **압박이 50% 를 넘으면 프로세스를 죽이는 정책**이 걸려 있다.
62GB 중 사용자 몫이 31GB 를 넘으면 발동한다. 학습 16GB + Chromium + VSCode 면 넘는다.

여기에 우리가 기름을 붓고 있었다. **체크포인트 저장 1회가 15.9GB 쓰기였다** —
`save_last: True` 때문에 `epoch=0-step=N.ckpt`(7.97GB)와 `last.ckpt`(7.97GB)를 매번 따로 썼고,
거기에 스냅샷 복사 7.5GB 가 겹쳤다.

## 9. 블렌드 후처리 — 이득이 재현되지 않았다 (정직한 기록)

### 9.1 아이디어

생성 영상과 정지영상을 α 로 섞어본다. DINO 는 static 이 좋고 Video 는 생성이 좋으니,
중간 어딘가에서 합이 최소가 될 수 있다는 발상이다. 두 방식을 만들었다.

```
mix(t)      = α·생성(t) + (1−α)·첫프레임
residual(t) = 첫프레임 + α·(생성(t) − 생성(0))     ← 재구성 오차를 상쇄하고 움직임만 얹는다
```

첫 프레임은 문제에서 **입력으로 주어진 사진**이므로 정답 정보를 쓰는 게 아니다(규칙 위반 아님).

### 9.2 두 번 쟀는데 결론이 달랐다

| 생성물 | 최소 지점 | TOTAL | static 대비 |
|---|---|---:|---|
| 배치 1 (누적 1000) | residual α=0.25 | 0.55838 | **−0.00194** |
| 배치 4 (누적 1000) | **α=0 (=static 그 자체)** | 0.56032 | 0.00000 |

**배치 4 생성물로는 어떤 α 도 static 을 못 이겼다.** 이유는 Action 에 있다.
배치 4 생성물은 원본 Action 이 1.2171 로 이미 최적이라, static(1.2402) 쪽으로 섞을수록 나빠지기만 한다.
반면 배치 1 생성물은 원본 Action 이 1.2435 로 static 보다 나빴기 때문에, 섞으면 중간에 최소가 생겼다.

> **그러므로 "블렌드로 static 을 이겼다"는 013 이후의 잠정 결론은 철회한다.**
> 이득 −0.00194 는 배치 효과의 불확실성(±0.007)보다 작다. **아직 static 을 확실히 이긴 적이 없다.**

### 왜 PL 표준 resume 을 못 쓰나

우리 체크포인트는 `save_weights_only: True` 라 **optimizer 상태가 아예 없고**,
`save_only_unet: True` 라 state_dict 에 UNet 만 있고 VAE·CLIP 키가 없다.
PL 1.9 는 재개 시 optimizer 상태를 찾다 KeyError 를 내고, strict 로드에서도 실패한다.
그래서 **가중치만 이어받는다**(UNet 1521키 100%). 잃는 것은 AdamW 모멘트와 lr 워밍업 진행도인데,
워밍업 250스텝이면 사실상 회복된다. 검증 로그: `적재 1521키 / 1440.505M / 불일치 0 / missing 0`.

## 14. 열린 질문·주의사항

- **붕괴가 점진적 발산인가, 2,000~3,000 사이 특정 시점의 사건인가.** 누적 2,500 평가로 좁히는 중.
  loss 가 누적 2400~2599 구간에서 평균 0.1011(최대 0.3698)로 튀었던 것이 단서일 수 있다.
- **학습률을 낮추면 정말 나아지는가.** 밤샘 A/B 가 답한다. 다만 1e-5 는 효과가 미미해
  3.5시간으로는 판별이 안 될 수도 있다.
- **Action 이 정답보다 좋은 이유를 아직 모른다.** "생성 영상이 매끄러워서"는 추측이다. 검증이 필요하다.
- **`artifacts/` 는 git 에 없다.** 체크포인트·생성영상은 이 컴퓨터에만 있다.
- **`open/baseline`, `open/submission_kit` 은 심볼릭 링크**로 `/home/rils/inha_challenge_datasets/` 를
  가리킨다. 즉 `/home/rils/dlacksdn/` **바깥**이며 읽기 전용 영역이다. 오늘 이 안의 파일은 수정하지 않았다.
- **프로젝트가 HDD(sda2, 회전디스크)에 있다.** NVMe SSD 는 Windows(NTFS) 파티션이라 못 쓴다.
  실행할 때마다 backbone 9.72GB + 체크포인트 7.97GB = 17.7GB 를 읽으므로 모델 로딩에 5분씩 걸린다.
- **손상 체크포인트 2개**: `1p1b/checkpoints/epoch=0-step=1500.ckpt`(2.7GB, 04:55 사고),
  `1p1b_r2/checkpoints/epoch=0-step=2250.ckpt`(368MB, 18:09 사고). 규칙상 지우지 않았다. 쓰면 안 된다.
- **학습 중에는 브라우저를 띄우지 말 것.** 메모리 압박 50% 를 넘기는 주범이다.
- **eval 데이터는 추론 입력으로만.** 지금까지 전부 train 홀드아웃만 사용했다.
