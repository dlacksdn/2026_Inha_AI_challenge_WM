### ② 009 §3 이 틀렸다 — 잔차는 이미 화면에 보인다 `[측정]`

009 §3: *"잔차 0.22 < uint8 1.0 → 반올림하면 사라진다. 지금 제출하면 static 과 픽셀 동일"*

`ck_001000` 으로 실제 mp4 를 만들어 디코드해 비교했다:

```
λ=1 vs static   |Δ| 평균 0.41~0.62   최대 60~76   픽셀의 29~38% 가 바뀐다
```

**평균으로 반올림 질문에 답한 것이 오류다.** 잔차 분포에 꼬리가 있어 일부 픽셀은 0.5 를 넘고,
x264 가 그 변화를 증폭해 인코딩한다.
⇒ **"잔차비 0.17 = 화면 등장 문턱", "step 2000 전엔 영상 뽑지 마라"는 폐기한다.**

### ③ "코사인으로 A/B 하지 마라"는 **지킬 수 없고, 틀렸다**

009 §7 과 인계 문서가 *"한쪽이 코사인을 직접 최적화하니 그걸로 비교하지 마라"* 고 했다.
①에 의해 로컬 채점이 봉인된 이상 **코사인 말고 비교자가 없다.** 그리고 코사인이 옳다:

```
출력 = 첫프레임 + λ·r̂ ,  λ 는 추론 때 곱하는 상수 하나 (공짜)
min_λ ‖r − λ·r̂‖² / ‖r‖²  =  1 − cos²
⇒ 크기는 λ 가 전부 흡수한다. 남는 판별량은 코사인 하나다
```

뭉갬 사다리(009 §1 눈금)도 **사영이라 최적 λ 가 정확히 1** 이다 —
그래서 **필요 코사인 0.96 이라는 눈금 자체는 그대로 유효하다.**

⚠ 타당한 걱정은 Goodhart 다: 코사인은 **얼어붙은 지도**를 통해서만 점수와 이어지고,
그 지도가 뭉갬 축 밖에서 맞는지는 ① 때문에 **이제 로컬로 확인할 수 없다.**
감수하는 위험이지 코사인을 버릴 이유가 아니다. 버리면 계기가 0 개다.

## 6. 재개 — 같은 분기점에서 두 팔

```bash
CK=artifacts/branchC/train_20260808_1809_g1/full_002500.pt

python scripts/branchC/train_c.py --tag g1r --steps 6000 --resume $CK
python scripts/branchC/train_c.py --tag dir  --steps 6000 --resume $CK --dir-loss --tau-alpha 0.1
```

**왜 step 0 이 아니라 분기인가** — 셋 다 이 설계의 이유다:

1. **wake 까지 기르는 2,500 스텝(구 카드 기준 3.3시간)을 두 팔 다 안 다시 산다**
2. **008 §1 이 실험 ③ 을 무효로 만든 결함이 구조적으로 사라진다.** 역사가 완전히 같고,
   재개는 `seed+1` 이므로 `[코드] train_c.py:284` **두 팔 모두 seed 1 → 데이터 순서까지 같다.**
   짝지은 비교라 씨앗 산포가 검정력을 먹지 않는다
3. **G2 가 살아난다.** 두 팔 다 6,000 까지 가면 wake+4,000 등록 판정이 그대로 나온다

**확인된 것** `[코드]`:
- `for step in range(start, args.steps)` (train_c.py:309) ⇒ `--steps 6000` 은 **총량**이다. 2,500 에서 3,500 스텝 더 간다
- `if step >= args.cal_step` (train_c.py:327) ⇒ 2,500 에서 재개해도 λ_c 가 **즉시** 교정된다. `--cal-step` 안 만져도 된다
- 새 디렉터리 `train_<시각>_{g1r,dir}/` 에 쌓인다. 원본은 안 덮어쓴다

**⚠ 위험 하나** `[추측]`: 방향항 팔이 L1 최적점 근처에서 출발한다.
step 0 부터 방향항을 켠 런이 다른(더 좋은) 해를 찾을 가능성은 못 본다. 이 예산으로는 확인 불가다.

### 96GB 를 쓰려면 — 유효배치 16 을 고정한 채로만

```bash
--micro-batch 8 --accum 2      # 곱이 16 이면 수학적으로 동일
```

⚠ **처음 20 스텝의 s/step 을 재고 결정하라.** 지금의 4.7 초/스텝은
`use_ckpt=True` 하드코딩 `[코드] train_c.py:291` + micro_batch 2, 즉 **32GB 에서 가능한 가장 느린 조합**의 값이다.
여기서 나오는 배율이 남은 시간 전체에 곱해진다 — 다른 어떤 항목도 이만한 레버가 없다.
