## 1. 이 프로젝트가 뭘 하는 건지 (처음 보는 사람용)

로봇 사진 **1장** 과 앞으로 할 행동 **16스텝×6축** 을 주면, 그 다음에 벌어질 **영상 16프레임**을 만들어내는 모델을 만드는 대회다.

채점은 세 가지를 섞는다. **전부 0에 가까울수록 좋다.**

| 성분 | 배점 | 무엇을 재나 | 쉽게 말하면 |
|---|---|---|---|
| **DINO** | 30% | DINOv2 라는 신경망이 각 프레임을 384개 숫자(의미 벡터)로 바꾼 뒤, 정답 프레임의 숫자와 얼마나 다른지(코사인 거리) | "장면이 정답과 의미적으로 같은가" |
| **Video** | 30% | R3D 라는 영상 신경망이 영상 전체를 512개 숫자로 바꾼 뒤 정답과 비교 | "영상 전체의 움직임이 정답 같은가" |
| **Action** | 40% | 생성 영상에서 로봇 관절각을 추출해 정답 관절각과 비교(MAE) | "영상만 보고 로봇이 뭘 했는지 읽었을 때 맞나" |

**중요한 사실 3개** (앞선 문서들에서 실측으로 확정된 것):

1. **Action(40%)은 사실상 상수다.** 정답 영상을 넣어도 1.223, 아무 정지영상이나 넣어도 1.240 이 나온다. 추출기가 단안 영상에서 깊이를 못 읽어서 생기는 한계라, **생성 품질로 못 바꾼다.** → 승부는 나머지 60%(DINO+Video)에서 난다.
2. **넘어야 할 상대는 주최측 baseline 이 아니라 "static" 이다.** static = 첫 프레임을 16번 복사한 정지영상. 아무것도 예측하지 않는데도 TOTAL 0.560 으로, 주최 baseline 11M(0.711)보다 **좋다**. 11M 은 정지에 가까운 장면에서 과하게 움직여(드리프트) 점수를 깎아먹었다.
3. **정답 영상도 거의 정지에 가깝다.** 프레임 사이 픽셀 변화량이 평균 4.81 뿐이다(11M 은 8.81 로 1.8배 과함). 그래서 "많이 움직이는 것"이 아니라 **작지만 정확한 움직임**이 목표다.

## 2. 지금 하고 있는 것 = branch B

**DynamiCrafter(DC) 라는 공개 사전학습 영상생성 모델의 큰 UNet(14억 파라미터)** 을 가져와, 우리 과제(로봇 행동 조건)에 맞게 이어서 학습시키는 노선이다.

- **UNet**: 확산모델의 심장. 노이즈를 조금씩 걷어내며 영상을 만들어내는 신경망.
- **warm-start(웜스타트)**: 백지에서 시작하지 않고, 이미 잘 학습된 가중치에서 출발하는 것. 우리는 DC 의 UNet 가중치 **1516개 키를 100% 그대로 로드**한다.
- 새로 배우는 건 **액션 분기 5개 키(165만 파라미터)** 뿐이고, 이건 **0으로 초기화**해서 시작한다(처음엔 액션이 결과에 영향 0 → 안전).
- 학습 범위는 `action_temporal` **551M(전체의 38%)** 만 풀고 나머지 889M 은 얼려둔다(VRAM 절약).

11M 노선은 이미 종결됐다: 재학습해도 DINO 0.481 로 static 0.123 근처에도 못 갔다.

## 4. 발견한 함정 3건 — 이게 이 세션의 최대 성과다

> 세 개 다 "코드는 멀쩡한데 결과가 이상한" 유형이라, 모르면 며칠을 날린다.

### 함정 ① 메모리 단편화 — 로그가 36분간 멈춘 이유

**증상**: 학습을 시작하면 로그가 한 줄도 안 나온다. GPU 사용률 7%, CPU 100%, 모든 스레드가 대기 상태.
에러도 안 나고 그냥 멈춘 것처럼 보인다.

**원인**: GPU 메모리(31.35GB)를 거의 다 쓰는 상황에서, PyTorch 가 메모리를 **잘게 쪼개진 조각**으로 갖고 있으면 큰 덩어리를 못 만든다. 그러면 계속 정리·재시도를 반복하며 사실상 멈춘다(스래싱).
*비유*: 창고는 비었는데 짐이 여기저기 흩어져 있어서 큰 상자를 놓을 자리가 안 나오는 상태.

**해결**: 학습·생성 전에 아래 환경변수를 준다. **한 줄로 끝난다.**
```bash
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
```
**효과**: 멈춤 → 정상 학습(2.5 s/it, loss 0.95→0.82 하강 확인).

### 함정 ② 단일 GPU 인데 DDP — OOM 과 속도 3배 손실의 원인

**증상**: ①을 고쳤는데도 3스텝 만에 `CUDA out of memory`. 게다가 속도가 8.72 s/it 로 매우 느림.

**원인**: config 에 `strategy: ddp` 가 박혀 있다. DDP 는 **여러 GPU 로 나눠 학습할 때** 쓰는 방식인데, GPU 가 1개면 이득은 0 이고 손해만 있다.
- 기울기(gradient)를 모으려고 **버킷 메모리를 추가로 잡는다** → OOM
- `find_unused_parameters` 때문에 **매 스텝마다 계산 그래프를 한 번 더 훑는다** → 느려짐

**해결**: config 파일은 건드리지 않고(다른 머신 재현성 보존), 실행할 때 **dotlist 인자로 덮어쓴다**.
```bash
lightning.trainer.strategy.target=pytorch_lightning.strategies.SingleDeviceStrategy \
lightning.trainer.strategy.params.device=cuda:0
```
> ⚠️ `strategy=single_device` 처럼 **문자열로 주면 실패**한다(`Device should be GPU, got cpu`).
> 코드가 문자열이면 그대로 넘기고 dict 면 `instantiate_from_config` 를 하기 때문에, **dict 형태로 device 까지 지정**해야 한다.

**효과**: OOM 3스텝 → **0회**, 8.72 s/it → **3.01 s/it (2.9배)**.

### 함정 ③ 생성할 때 EMA 구멍 — 결과를 조용히 노이즈로 만든다 (가장 위험)

**증상**: 학습은 잘 됐는데 **생성한 영상이 전부 "지지직"** 거린다. 그런데 에러는 하나도 안 난다.
채점하면 DINO 0.94 가 나와서, 모르면 **"1.1B 노선 실패"로 잘못 결론 내린다.**

**숫자로 본 증상**:
| | 프레임 사이 픽셀 변화 | std |
|---|---|---|
| 정답 영상 | 3.93 ~ 4.01 | 30 ~ 67 |
| 버그 상태 | **103** (프레임끼리 완전 무관 = 난수) | **90** |

**원인** (`lvdm/ema.py` 17~18행, 51~52행):
- **EMA** 는 학습 중 가중치의 "이동평균 사본"을 따로 갖고 있다가, 생성할 때 그걸 쓰는 기능이다(보통 더 부드러운 결과가 나옴).
- LitEma 는 **학습 대상(requires_grad)인 파라미터만** 사본을 만든다.
- **학습할 때**: 551M 만 학습하므로 EMA 사본도 551M 어치(809키)만 저장된다.
- **생성할 때**: 학습 범위 설정을 안 하니 **전체 파라미터가 학습 대상으로 취급**된다 → LitEma 가 1521키 전부를 **모델 생성 직후의 랜덤 가중치**로 채운다.
- 체크포인트를 `strict=False` 로 얹으면 809키만 덮이고 **712키는 랜덤인 채로 남는다.**
- 생성 코드가 `ema_scope()` 안에서 돌기 때문에, 그 랜덤값이 **UNet 절반을 덮어쓴다** → 노이즈.

*비유*: 학습한 뇌를 넣어야 하는데, 학습 안 한 백지 뇌의 절반을 덮어씌우고 그림을 그리라고 한 셈.

**해결**: 생성할 때만 EMA 를 끈다. 학습된 가중치는 체크포인트의 `model.diffusion_model.*` **1521키에 온전히 들어 있으므로**, EMA 없이 그대로 쓰는 게 정확하다.
→ `run_1p1b_generate.sh` 가 생성 전용 config 사본에 `use_ema: False` 를 자동 주입하도록 수정 완료(커밋 `a929a4f`).

**효과**: 프레임 변화 103 → **1.56~2.37** (정답 3.93~4.01 과 같은 대역), DINO 0.94 → **0.221**.

> **교훈**: "학습이 덜 됐나?" 라고 넘기기 전에 **생성물을 눈으로 봐야 한다.** 이번엔 사용자가 영상을 직접 열어보고 지적해서 잡혔다.
> 그리고 검증할 때는 **EMA 에 있는 키(액션 분기)만 보면 안 되고, EMA 에 없는 동결 파라미터도 확인**해야 한다. 이 세션의 첫 검증이 그걸 놓쳤다.

### 5.1 채점 결과 (홀드아웃 96표본, 낮을수록 좋음)

| 예측기 | DINO | Video | Action | **TOTAL** |

### 5.2 학습곡선 (500 → 1000 스텝)

```
DINO   0.24191 → 0.22074   (−0.0212, −8.8%)
Video  0.10084 → 0.08494   (−0.0159)  ← 이 구간에서 static 0.0911 을 가로질러 내려감
TOTAL  0.59684 → 0.58911   (−0.0077)
```
**세 성분 모두 우하향** = 학습이 실제로 성능을 올리고 있다. 그림: `artifacts/branchB/loss_dino_curve.png`

### 5.3 목표 역산 — 얼마나 더 줄이면 이기나

Video·Action 을 지금 값으로 고정하면
```
0.3·DINO + 0.3·0.08494 + 0.4·1.24352 < 0.56032
→ DINO < 0.1248
```
**DINO 를 0.125 아래로 내리면 static 을 이긴다.** 현재 0.221 이므로 **0.096 더** 줄이면 된다.
직선으로 이어진다고 보면 500스텝당 0.021 → 약 2,300 스텝 더 필요(총 ~3,300 스텝 = 원래 계획한 5시간 학습량).
**단 점이 2개뿐이라 곡선 모양(직선이냐 포화냐)은 알 수 없다. 세 번째 점이 필요하다.**

### 5.4 loss 는 왜 쓸모가 없나 (중요)

학습 loss 는 **거의 평탄**했다: 전반부 평균 0.0735 → 후반부 0.0708 (−3.6%, 노이즈 범위).
개별 값은 0.009~0.275 로 30배나 널뛴다.

**이유**: 확산모델은 스텝마다 **랜덤한 타임스텝 t**(노이즈를 얼마나 씌울지)를 뽑아 loss 를 잰다. t 가 크면 loss 도 크게 나오는데, 이건 모델 실력과 무관하다. 게다가 warm-start 라 "노이즈 제거" 실력은 이미 좋아서 loss 가 움직일 여지가 적다.

**결론: 이 프로젝트에서 loss 는 "터졌는지" 확인용이다. 진척은 홀드아웃 채점(DINO)으로만 판단한다.**
(도구: `scripts/branchB/loss_curve.py` — 구간평균으로 추세만 본다)

## 9. 열린 질문·주의사항

- **추론 속도 26초/샘플이 예산을 넘는다.** M1 실측(9.78초/샘플)의 2.7배다. 이번 실행은 `use_ema=False` 라 EMA 전환은 원인이 아니다.
  후보: `perframe_ae: True`(16프레임을 하나씩 VAE 디코드), `fs_condition` 추가 연산, fp32 가중치.
  → **제출 파이프라인 설계 전에 반드시 규명해야 한다.** (대회 기준: 216샘플 ≤ 1시간, RTX PRO 6000 1대)
- **resume 배선 없음.** 학습 재개가 warm-start 부터 다시 시작한다.
- **학습곡선 점이 2개뿐**이라 외삽은 근거가 약하다. 세 번째 점 전에는 "몇 스텝이면 이긴다"고 단정하지 말 것.
- **step=1500.ckpt(2.7G)는 손상 파일**이다. 쓰면 안 되고, 규칙상 지우지도 않았다.
- **GPU 작업 중에 무거운 CPU 작업을 겹치지 말 것.** 오늘 생성 작업이 15분간 멈춘 적이 있는데,
  원인은 GPU 가 아니라 **스왑 스래싱**이었다. 검증용 CPU 스크립트(모델을 CPU 에 올리면 ~18GB RAM)와
  체크포인트 복사(7.5GB)가 겹쳐 메모리·페이지캐시를 채우자, 생성 프로세스가 스왑으로 밀려났고
  이 머신의 스왑은 **HDD(회전 디스크)** 라 25MB/s 로 되읽느라 멈춘 것처럼 보였다.
  → 증상이 "GPU 는 노는데 프로세스는 살아있음" 이면 `free -g` 와 `/proc/<pid>/status` 의 `VmSwap` 을 볼 것.
- **Action(40%)은 여전히 상수**다(1.235~1.244). 이 성분은 개선 대상이 아니다.
- **`artifacts/` 는 git 에 없다.** 체크포인트·생성영상은 이 컴퓨터에만 있다. push 해도 안 올라간다.
- **eval 데이터는 추론 입력으로만.** 학습·데이터선별에 쓰면 실격이다. 지금까지 전부 train 홀드아웃만 사용했다.
