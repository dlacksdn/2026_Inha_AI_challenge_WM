## 1. 먼저 알아야 할 용어 (이 문서에서 쓰는 말)

007 §3의 용어사전에 없는 것, 또는 이번에 처음 중요해진 것만 모았다.

### 1-A. 가중치를 "얹는다"는 게 무슨 일인가

```
신경망 = (층 이름 → 숫자 덩어리) 사전(dictionary)
         예: "input_blocks.1.0.emb_layers.1.weight" → 320×1280 행렬

사전학습 가중치를 얹는다 = 남이 학습해 둔 사전을 내 신경망의 같은 이름 칸에 복사한다
   이름이 같고 크기(shape)도 같아야 복사된다. 하나라도 다르면 그 칸은 비어(랜덤) 남는다.
```

| 용어 | 뜻 | 이 프로젝트에서 |
|---|---|---|
| **state_dict** | 위의 "(층 이름 → 숫자)" 사전 그 자체 | 우리 1.1B UNet은 1521칸, DC 사전학습은 1516칸 |
| **키(key)** | 사전의 이름 하나 = 층 하나의 파라미터 | `time_embed.2.weight` 같은 문자열 |
| **shape** | 숫자 덩어리의 모양 | `[640, 1280]` = 1280개를 받아 640개를 내놓는 층 |
| **strict=False** | "이름이 안 맞는 칸은 그냥 넘어가라"는 옵션 | **주의: 이름은 맞고 shape 만 다르면 넘어가지 않고 에러가 난다**(§4) |
| **missing** | 사전에 없어서 **랜덤으로 남은** 칸 목록 | 우리는 7개가 정상 |
| **unexpected** | 사전에는 있는데 내 신경망엔 없는 칸(버려짐) | 0개가 목표 |
| **스크래치(scratch)** | 사전학습 없이 처음부터 학습해야 하는 부분 | 액션 분기 등 |
| **warm-start** | 학습된 가중치에서 이어 학습하기 | branch B 의 전제 |

### 1-B. UNet 안에서 "시간"과 "액션"이 흐르는 길 (이번 발견의 무대)

확산 모델의 UNet은 "지금이 몇 번째 노이즈 제거 단계인지(timestep)"를 숫자 벡터로 만들어
**모든 층에 뿌린다**. 그 벡터를 만드는 곳이 `time_embed`이고, 각 층에서 그것을 받는 창구가 `emb_layers`다.

```
       timestep(t)
          │
     [ time_embed ]  ← 3층짜리 작은 신경망. 마지막 층 이름이 time_embed.2
          │  1280차원 벡터
          ├──────────────► emb_layers (사전학습된 1514개 층이 전부 이걸 받는다)
```

우리 모델은 여기에 **액션(6차원 × 16스텝)** 을 추가로 실어야 한다. baseline 코드는 두 방식을 지원한다.

```
[방식 1: concat = 이어 붙이기]  (baseline 기본값, 009 스펙)
   time_embed 가 640차원만 만들고 | 액션이 640차원을 만들어 | 둘을 옆으로 붙여 1280차원
   → time_embed 의 마지막 층이 "1280→640" 이 된다. DC 원본은 "1280→1280" 이므로 **모양이 달라 못 얹는다.**
   → 즉 time_embed.2 가 랜덤이 되고, 그 랜덤 벡터가 사전학습된 1514개 층 전부로 흘러간다.

[방식 2: add = 더하기]  (add_act_time_emb=True)
   time_embed 가 1280차원 그대로 만들고 | 액션도 1280차원을 만들어 | 둘을 **더한다**
   → time_embed 의 마지막 층이 "1280→1280" 이라 DC 것을 그대로 얹을 수 있다. (액션 분기만 랜덤)
```

| 용어 | 뜻 |
|---|---|
| **`time_embed.2`** | 시간 정보를 만드는 마지막 층. 여기가 랜덤이면 **모든 층이 엉뚱한 시간 신호를 받는다** |
| **`emb_layers`** | 각 블록이 시간(+액션) 벡터를 받는 창구. 사전학습이 잘 되어 있는 부분 |
| **`use_scale_shift_norm`** | 그 창구가 출력 크기를 2배로 쓰는 옵션. True면 DC와 모양이 안 맞아 46키가 막힌다 → **False로 끔** |
| **`fs_condition` / `fs`** | "초당 몇 프레임 영상인지"를 모델에 알려주는 조건. 켜면 DC의 `fps_embedding` 4키까지 받는다. 학습 시 값은 데이터셋 메타의 fps(우리 데이터=6)가 자동으로 들어간다 |
| **`add_act_time_emb`** | 위 방식 2 스위치. **이미 구현돼 있다**(`openaimodel3d.py` 419~434행, forward의 `emb = time_emb + act_emb`) |
| **0초기화(zero-init)** | 새 분기의 마지막 층을 0으로 시작시켜, 초기에는 아무 영향도 주지 않게 하는 기법. baseline이 `fps_embedding`에 이미 쓴다(451~452행) |

### 1-C. "예측이 진짜인가"를 판정하는 통계 도구 (§5에서 씀)

| 용어 | 쉬운 설명 | 왜 필요한가 |
|---|---|---|
| **oracle(오라클)** | **정답을 미리 보고** 표본마다 최선을 고른 가상의 성적 | 실현 불가능한 상한선. "적응이 최대 얼마나 벌어줄 수 있나"의 천장 |
| **LOO-CV** (leave-one-out 교차검증) | 96개 표본 중 1개를 빼고 나머지 95개로 규칙을 만들어, 뺀 1개를 맞혀보기 — 96번 반복 | 자기 답안을 보고 규칙을 만드는 **자기기만(누출)** 을 막는다 |
| **셔플 대조군** | 입력 특징만 무작위로 섞어 같은 절차를 반복 | 우연히 잘 나온 것과 진짜 신호를 구별한다(008 §2에서 쓴 것과 같은 장치) |
| **회수율** | (예측 정책의 이득) ÷ (oracle 의 이득) | "이론상 최대치의 몇 %를 실제로 가져왔나" |

### 4.1 규명한 함정 2개 (둘 다 학습을 0스텝에서 죽인다)

**함정 A — `strict=False`도 shape 불일치는 막지 못한다.**
PyTorch의 `load_state_dict(..., strict=False)`는 "이름이 없는 칸"만 봐준다.
**이름은 있는데 모양이 다르면 `RuntimeError`를 던진다.** 우리 경우 `time_embed.2` 2키가 정확히 그렇다.

```
결론: config 의 only_reload_modules 에 "model.diffusion_model" 을 넣으면 → 학습 시작 즉시 죽는다.
      UNet 로드는 런처가 "shape 불일치 키를 먼저 빼고 → strict=False 로드" 순서로 해야 한다.
      (M3 Part B의 warm-start 패턴과 같고, 이번에 그 로직을 검증까지 마쳤다.)
```

**함정 B — `lvdm/common.py`가 `torch.utils.checkpoint`를 임포트 없이 쓴다.**
학습 경로에서는 pytorch_lightning이 우연히 먼저 임포트해줘서 문제가 없었다. 우리처럼
`import torch`만 하는 스크립트에서는 `AttributeError`가 난다 → 우리 쪽에서 임포트해주면 끝.

## 5. 이번의 핵심 발견 — "99.89%"는 함수 보존을 뜻하지 않는다

### 5.1 왜 의심했나

99.89%는 **파라미터 개수의 비율**이다. 그런데 §1-B에서 봤듯이, concat 방식에서 랜덤으로 남는
`time_embed.2`는 **사전학습된 1514개 층 전부에 신호를 뿌리는 지점**이다.
숫자상 0.11%지만, 위치가 급소다. 그래서 "비율"이 아니라 **입출력 함수**를 직접 비교했다.

### 5.2 방법

같은 입력(고정 시드)에 대해 UNet 출력을 3가지 구성에서 뽑아 비교했다. (CPU, 각 40초)

```
REF    : action_conditioned=False  → 액션 분기가 아예 없는 = DC 원본 UNet 그 자체(1516키 100% 로드)
CONCAT : 우리 현 스펙(액션 이어붙이기, time_embed.2 랜덤)
ADD    : 우리 스펙 + add_act_time_emb=True(액션 더하기, time_embed.2도 사전학습 로드)
```

### 5.3 결과 (`results/branchB/warmstart_init_probe.json`)

| 구성 | DC 가중치 흡수 | REF와 코사인 | REF와 상대오차(L2) | 출력 std |
|---|---:|---:|---:|---:|
| REF (기준) | 1438.86M / **100.000%** | +1.00000 | 0.00000 | 0.3315 |
| **CONCAT (현 스펙)** | 1437.21M / 99.886% | **+0.66612** | **0.93572** | 0.4082 |
| **ADD** (액션=0) | 1438.86M / **100.000%** | **+1.00000** | **0.00000** | 0.3315 |
| **ADD** (랜덤 액션) | 1438.86M / 100.000% | **+0.99846** | 0.05547 | 0.3316 |

읽는 법:

- **CONCAT은 액션을 0으로 줘도** 출력이 원본과 상대오차 0.94만큼 다르다. 사전학습된 "영상 만드는 능력"이
  초기부터 거의 작동하지 않는다는 뜻이다. 학습으로 되찾을 수는 있지만, **4일 단발 학습에서 왜 그것부터
  다시 배워야 하는지** 정당화가 필요하다.
- **ADD는 액션이 0일 때 원본과 완전히 동일**하다(코사인 1.00000, 오차 0.00000).
  랜덤 액션을 넣어도 교란이 5.5%뿐이다. 즉 **"DC를 그대로 시작점으로 삼고 액션만 새로 배우는" 상태**가 된다.
- 추가로, `action_embed`의 마지막 층을 **0초기화**하면(baseline이 `fps_embedding`에 쓰는 기법)
  랜덤 액션에서도 초기 출력이 REF와 정확히 같아진다 → 교란 0에서 출발한다.

### 5.4 그리고 009 §2.2의 사실오류

> 009 §2.2: "액션 주입을 concat → 가산으로 바꾸면 100% 로드가 된다. **코드 수정이 필요하므로**
> 우선 현행 concat으로 진행하고 초기 학습이 불안정하면 이 옵션을 시도한다."

**코드 수정은 필요하지 않다.** `add_act_time_emb` 플래그가 baseline UNet에 이미 구현돼 있다
(`__init__` 419~434행에서 분기 크기를 바꾸고, `forward`에서 `emb = time_emb + act_emb`).
config 한 줄이므로 "불안정하면 나중에"가 아니라 **처음부터 고를 수 있는 선택**이다.

### 5.5 판단이 필요한 지점 (권고 포함)

| | concat (009 현 스펙) | add (+0초기화) |
|---|---|---|
| DC 사전학습 흡수 | 99.886% (time_embed.2 버림) | **100%** |
| 초기 함수 보존 | cos 0.666 / 오차 0.94 (**사실상 파괴**) | **cos 1.000 / 오차 0.000** |
| 액션 표현 용량 | 전용 640차원 채널 | 시간 임베딩과 같은 1280차원 공간을 공유(더하기) |
| 근거 | — | Vid2World가 쓰는 방식(002) |
| 미측정 위험 | — | 액션 신호가 시간 신호에 묻힐 수 있다(학습 후 우열은 미측정) |

**권고: add + `action_embed` 마지막 층 0초기화로 변경.** branch B의 존재 이유가 "DC 사전학습 이득"인데
concat은 그 이득을 시작부터 대부분 버린다. 다만 이는 009 스펙 변경이므로 **사용자 승인 후** 반영한다.
(승인 시 A/B로 남겨둘 수도 있다 — 009 §3.1의 A/B 항목 3에 이미 "concat vs 가산"이 들어 있다.)

## 6. 질문 4 판정 — 액션 기반 적응형 모션 스케일은 **음성**

### 6.1 무엇을 물었나

008 §1.5에서, 표본마다 최적 모션량이 다르고 **정답을 보고** 고르면 −2.1%p를 얻는다는 것을 알았다.
정답 없이 항상 갖고 있는 정보는 **액션(16×6)** 이다. 그걸로 최적 모션량을 맞힐 수 있나?

### 6.2 방법 (누출 방지 장치 3개)

- 액션을 채점기와 동일한 z공간으로 정규화한 뒤 특징 12개 추출(이동량, 경로길이, 스텝 최대·표준편차, 관절별 경로 등)
- **LOO-CV 96폴드**: 표본 i를 고를 때 i의 점수를 절대 쓰지 않는다
- **정규화 강도(alpha)도 폴드 안에서만** 5-fold로 선택(하이퍼파라미터 누출 차단)
- **셔플 대조군 20회**: 특징만 무작위로 섞어 같은 절차 반복

### 6.3 결과 (`results/branchB/action_adaptive_scale.json`, n=96, 0에 가까울수록 좋음)

| 정책 | TOTAL | DINO | Δ vs static | t | 승률 |
|---|---:|---:|---:|---:|---:|
| static | 0.56154 | 0.12413 | 0 | — | — |
| 고정 최선 `motion_b0.10` | 0.56040 | 0.13173 | −0.00114 | −0.64 | 47% |

| 예측 정책(24변형 중 선택) | 0.56224 | 0.13201 | **+0.00070** | +0.45 | 45% |
| 예측 정책(motion 계열) | 0.56183 | 0.13156 | **+0.00029** | +0.20 | 40% |

- 예측 정책 3종이 **모두 셔플 분포 안**에 있고 static보다도 나쁘다. **oracle 회수율 0%.**
- 표본별 최적 b와 액션 특징의 상관은 |r| ≤ 0.17(최대 `grip_range` −0.168) — 사실상 없다.
- 최적 b의 분포: b=0(정지) 29개, 0.05 13, 0.1 19, 0.2 15, 0.4 12, 0.6 6, 0.8 2 → 넓게 퍼져 있지만
  그 흩어짐이 **액션으로 설명되지 않는다.**

### 6.4 그리고 더 중요한 관찰

oracle의 −2.1%p는 **DINO를 악화시키면서**(static 0.12413 → oracle 0.15913) 얻어진다.
즉 이 이득의 정체는 Action(40%)·Video의 트레이드오프를 파먹는 것이고,
**우리가 성공 판정 지표로 정한 DINO와는 반대 방향**이다(009 §5). 게다가 eval에서는 성분 비중이
로컬과 다르다(008 §4.3). ⇒ 회수 가능했더라도 쫓을 가치가 낮았다. **이 노선은 닫는다.**

## 11. 한 문단 결론

S1~S3은 통과했다 — 1.1B config가 있고, DC 사전학습은 실제로 99.885%가 올라가며, 남는 랜덤 부분은
예측한 7키뿐이고, CPU forward까지 돈다. 그러나 이번 세션의 진짜 수확은 **"비율은 함수가 아니다"** 라는
발견이다. 현 스펙(액션 이어붙이기)은 파라미터의 99.89%를 받아오면서도, 사전학습된 능력은
